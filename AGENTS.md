# AGENTS.md

Guidance for AI coding agents working on this repo: maintaining the Ubuntu
fix, or porting it to another distro (Fedora, Arch, openSUSE, NixOS, ...).
Read `README.md` first for the user-facing summary. Agents for other tools
(e.g. `CLAUDE.md`) should treat this file as the source of truth.

## User requirements (non-negotiable)

- **Don't add third-party package sources to the system**: no PPAs, COPR, AUR
  helpers, Flatpak remotes, or random GitHub repos (including brainchillz's
  fix, which inspired this one). The fix must come from **upstream projects**
  (linux-firmware, alsa-ucm-conf, the mainline kernel) or from files in this
  repo.
- **Reproducible.** Pin sources to exact commits and verify firmware by SHA256.
  Other PX13 owners must get the same result.
- **Reversible and minimal.** Everything must be undoable with
  `install.sh --uninstall`. Never overwrite or edit files owned by a distro
  package; add new files, or generated overrides that follow package updates.
- **Don't build or replace kernel modules** unless there's no alternative. The
  driver is already in mainline.
- **Never use amp firmware from another laptop model.** It contains
  speaker-protection tuning; wrong values can physically damage the speakers.
  Only files for subsystem `1714` are valid for this machine.

## The hardware and what was wrong

- ASUS ProArt PX13 HN7306 (Strix Halo). Audio coprocessor: AMD ACP, PCI
  `1022:15e2`, subsystem `1043:1714`, driver `snd_pci_ps`.
- SoundWire link 1 has three devices: a Realtek `rt721-sdca` (headset jack)
  and two **TI TAS2783** smart amps (`sdw:0:1:0102:0000:01:8` and `...:01:b`),
  driven by mainline `snd-soc-tas2783-sdw`.
- ALSA card `amdsoundwire`. PCM device 2 (`SDW1-PIN1-PLAYBACK-SmartAmp`) is the
  speakers.

There were three independent problems:

1. **Missing amp firmware.** The driver requests `<PCI subsystem>-<link>-<unique id>.bin`,
   i.e. `1714-1-8.bin` / `1714-1-B.bin`. Kernel ≥ 7.2 requests
   `1714-1-0x8.bin` first and falls back to the old name. TI added the real
   files to linux-firmware in commit `2f90f4fe` (2026-05-19) as
   `ti/audio/tas2783/1714-1-0x{8,B}.bin`, with root-level `Link:` entries in
   `WHENCE`. Symptom: `error playback without fw download`, followed by
   `hw_params -22`.
2. **Missing UCM profile.** No `sof-soundwire/tas2783.conf`, and the AMD
   machine driver doesn't put `spk:tas2783` in the card components string
   (`amixer -c1 info` shows only `cfg-amp:2 mic:acp-dmic cfg-mics:1 hs:rt721`),
   so PipeWire shows "Dummy Output". TI added `tas2783.conf` upstream in
   alsa-ucm-conf commit `182d0122a7` (2026-07-17). Even with that file, this
   kernel needs `SpeakerCodec1 "tas2783"` forced in a card-specific override.
3. **Amps lose firmware on s2idle resume** (kernel bugzilla 221798, open).
   Reported on cold boot: an intermittent `-110` firmware-download timeout.
   Workaround: unbind/bind the ACP PCI device, which re-enumerates SoundWire
   and re-downloads the firmware, then restart WirePlumber.

## What we ran to diagnose it (reuse these on any distro)

```sh
cat /sys/class/dmi/id/product_name                     # model
lspci -nn | grep -iE 'audio|multimedia'                 # ACP 1022:15e2
cat /sys/bus/pci/devices/*/subsystem_device            # 0x1714
ls /sys/bus/soundwire/devices/                          # amps present?
for d in /sys/bus/soundwire/devices/sdw:*; do echo "$d $(cat $d/status) $(readlink $d/driver)"; done
journalctl -k -b | grep -iE 'tas2783|firmware'          # exact firmware filename requested
aplay -l; amixer -c1 info; amixer -c1 controls          # PCMs, components, "Left Spk Switch" etc.
ls /lib/firmware/ti/audio/tas2783/                      # what the distro ships
ALSA_CONFIG_UCM2=/path/to/copy/ucm2 alsaucm -c hw:1 dump text   # test UCM changes without root
aplay -D hw:amdsoundwire,2 -f S16_LE -r 48000 -c 2 -d 1 /dev/zero  # raw amp test (silent)
wpctl status                                            # does PipeWire see "Speaker"?
```

Also read the driver source for the running kernel version
(`sound/soc/codecs/tas2783-sdw.c`) to check the filename format and header
parsing before trusting any blob.

## What the Ubuntu install does (install.sh)

| Installs | Path | Notes |
|---|---|---|
| Firmware | `/lib/firmware/updates/ti/audio/tas2783/1714-1-0x{8,B}.bin` + symlinks `1714-1-{8,B}.bin`, `1714-1-0x{8,B}.bin` | `updates/` has the highest priority in the kernel's firmware search path and isn't owned by any package |
| UCM | `/usr/share/alsa/ucm2/sof-soundwire/tas2783.conf` | skipped if a package owns it (`dpkg -S`) |
| UCM override | `/usr/share/alsa/ucm2/conf.d/amd-soundwire/<card longname>.conf` | generated by `px13-audio-ucm-sync` from the stock `amd-soundwire.conf`; alsa-lib loads `<longname>.conf` before `<driver>.conf` |
| apt hook | `/etc/apt/apt.conf.d/99px13-audio` | regenerates the override after dpkg runs |
| Self-heal | `/usr/local/sbin/px13-audio-check`, `px13-audio-{boot,resume}.service` | polls for up to 20 s; resets ACP only if the amps fail |
| initramfs | `update-initramfs -u` | only if the tas2783 module is in the initramfs |

Things that didn't work, so don't retry them: a thin UCM wrapper file that
`Include`s the stock `amd-soundwire.conf` and sets `Define.SpeakerCodec1`
before or after it. The stock file's own `Define` block resets the variable,
so the override must be a full generated copy.

Lessons learned:
- Firmware download over SoundWire takes a few seconds after the amps attach.
  Never test the amps right after a reset; poll instead.
- WirePlumber can get stuck on "Dummy Output" after the card disappears and
  comes back. Restart the user's `wireplumber pipewire pipewire-pulse`.
- `PIN4-CAPTURE-SmartAmp ... transport params failed -22` is the amps' I/V
  sense capture stream, which WirePlumber probes. It's harmless for playback.

## Porting to another distro: how to think about it

**Step 1: check what's already fixed upstream on that distro.** Most of this
repo becomes unnecessary as distros catch up. Check, in order:

1. Does the distro's linux-firmware include `ti/audio/tas2783/1714-1-0x8.bin`
   (possibly `.xz`/`.zst`-compressed)? If yes, skip the firmware step. Still
   check the name the *running kernel* requests: kernel ≤ 7.1 needs the
   `1714-1-8.bin` alias, which upstream doesn't provide.
2. Does alsa-ucm-conf include `sof-soundwire/tas2783.conf`? If yes, skip it.
3. Does the card components string contain `spk:tas2783`? If yes, the
   generated override isn't needed.
4. Does audio survive suspend/resume? If yes, skip the self-heal units.

Only install the layers that are still missing.

**Step 2: map the Debian-specific pieces** (everything else in install.sh is
distro-neutral: sysfs, systemd, `/lib/firmware/updates`, `/usr/share/alsa/ucm2`):

| Piece | Debian/Ubuntu | Fedora / RHEL | Arch | openSUSE |
|---|---|---|---|---|
| "Is this file package-owned?" | `dpkg -S f` | `rpm -qf f` | `pacman -Qo f` | `rpm -qf f` |
| Re-sync after package updates | `/etc/apt/apt.conf.d` `DPkg::Post-Invoke` | dnf5 `actions` plugin (`/etc/dnf/libdnf5-plugins/actions.d/*.actions`) or a systemd path unit watching `amd-soundwire.conf` | pacman hook in `/etc/pacman.d/hooks/*.hook` | zypp plugin, or the systemd path unit |
| Rebuild initramfs | `update-initramfs -u` | `dracut -f` | `mkinitcpio -P` | `dracut -f` |
| List initramfs contents | `lsinitramfs` | `lsinitrd` | `lsinitcpio` | `lsinitrd` |

A **systemd `.path` unit** watching `/usr/share/alsa/ucm2/conf.d/amd-soundwire/amd-soundwire.conf`
is the distro-neutral replacement for the apt hook. Prefer it when porting.

Distro notes:
- **Fedora**: tracks linux-firmware and alsa-ucm-conf closely, so layers 1 and
  2 are probably already fixed; check before installing anything. With
  SELinux enforcing, run `restorecon -R` on files copied into `/lib/firmware`
  and `/usr/share/alsa`. Firmware may be `.xz`-compressed; the kernel
  handles that transparently.
- **Arch**: rolling release, and likely has everything except the resume bug.
  Use `linux-firmware` from the official repos, not the AUR.
- **Silverblue / Kinoite / other immutable distros**: `/usr` is read-only.
  For firmware, add the kernel parameter
  `firmware_class.path=/var/lib/px13-audio/firmware` and put the files there. UCM can't be added under
  `/usr`; wait for the distro's alsa-ucm-conf, or layer a package with
  `rpm-ostree` (that's a local package, not a third-party repo; ask the user).
- **NixOS**: do it declaratively. Firmware via `hardware.firmware` (a
  derivation containing the two blobs), UCM via an overlay on
  `alsa-ucm-conf`, and self-heal as `systemd.services`. Don't write to
  `/usr` or `/lib`.

**Step 3: verify**, in this order: the kernel log shows no `without fw download`,
the raw `aplay` test succeeds, `wpctl status` shows a Speaker sink, audible
left/right test (`pw-play /usr/share/sounds/alsa/Front_Left.wav`), then reboot,
then suspend/resume.

## When to delete things from this repo

- Distro ships linux-firmware ≥ 20260519 **and** kernel ≥ 7.2: drop the firmware step.
- Distro ships alsa-ucm-conf with `182d0122a7` **and** the kernel emits `spk:tas2783`: drop UCM.
- Bug 221798 fixed in the running kernel: drop the resume unit (keep the boot
  check only if `-110` boot failures are still seen).

## Repo conventions

- POSIX `sh` for scripts (`sh -n` must pass; shellcheck-clean if available).
- Keep `firmware/*.bin` byte-identical to upstream (TI TSPA forbids
  modification) and update `firmware/SHA256SUMS` + the pinned commit together.
- MIT for our files; `ucm2/` stays BSD-3-Clause (alsa-ucm-conf); firmware under
  `firmware/LICENCE.ti-tspa`.
